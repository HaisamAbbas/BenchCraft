# G22.3 — Distributed application workers

## What runs where

`aibench run --workers N` starts a coordinator API in the run process and waits for `N`
application workers to connect. Workers make outbound authenticated requests to the coordinator,
lease application invocations, and return their outcomes. They do not open or mount the
coordinator's SQLite workspace. The run engine remains the only owner of work-item state,
budgets, retries, artifacts, evaluator calls, and run history.

The coordinator freezes the application's canonical spec hash in the run. A connecting worker
must present the same spec hash, protocol, and BenchCraft version. It must have the application's
configured code, runtime, credentials, and other dependencies installed locally. Non-container
apps need an owner-declared `revision` or `environment_digest`; a container pinned by digest and
without host mounts is also accepted. The coordinator does not copy application source or secrets
to a worker.

Only the app-visible case projection is sent. Reference answers, metadata, and non-app-visible
fixtures remain in the coordinator. Workers send a bounded JSON outcome, including restricted raw
captures when the runner produces them; the coordinator verifies the response and commits those
captures and the execution result to its own artifact store and SQLite database. Cache keys,
attempt numbers, evaluator spending, and retries stay under coordinator control.

## Start a coordinator and workers

The coordinator token must be 32–4096 visible ASCII characters, set in the named environment
variable on the coordinator and each worker, and approved in the run policy as a secret reference.
Add `env:AIBENCH_WORKER_TOKEN` to the policy's `allowed_secret_refs`. For example, a loopback
development run can use:

```powershell
$env:AIBENCH_WORKER_TOKEN = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
aibench run --plan plan.json --workers 1 --worker-port 8765
```

The coordinator prints a `worker connect` command after it binds. Replace the
`APP_CONFIG_PATH_ON_WORKER` placeholder with the application config path on each worker host, and
set the same token environment variable there. Each worker process polls the coordinator until it
is stopped. For more capacity, start additional worker processes and select `--capacity` to match
each host's safe application concurrency.

For remote hosts, bind the coordinator to a reachable interface, provide a server certificate and
private key, and advertise an HTTPS URL workers can resolve. Workers verify TLS by default; a
private CA can be passed as `worker connect --ca-bundle FILE`.

```powershell
aibench run --plan plan.json --workers 2 --worker-host 0.0.0.0 --worker-port 8765 `
  --worker-advertise-url https://bench.example:8765 `
  --worker-tls-cert coordinator.crt --worker-tls-key coordinator.key
```

The coordinator refuses a non-loopback listener without TLS. A worker refuses a non-loopback
plain-HTTP coordinator URL. The API authenticates every request with a bearer token, compares it
in constant time, rejects duplicate/transfer-encoded headers, and limits request/response bodies,
captures, worker count, and concurrent connections.

## Dispatch and recovery behavior

Workers lease invocations up to their configured capacity and heartbeat active leases every
10 seconds. The coordinator accepts a result only from the worker holding that live lease and
only when its correlation ID matches. A duplicate identical result is idempotent. A different or
late result is refused. Leases expire after 45 seconds without a heartbeat; an expired, already
leased invocation is recorded as an error with a conservative effect state (unknown for an
effectful application) and is not reassigned. The
existing engine retry rules then decide whether another attempt is safe from the application's
declared effect level. A coordinator process crash is recovered from its durable work graph using
the existing run recovery rules; the API queue and worker leases themselves are process-local.

The first API version supports runs whose frozen reset mode is `none`. It refuses runs that
depend on per-case or per-episode reset because a reset and invocation must be guaranteed to run
on the same worker as one atomic operation. `run --detach` is refused with this mode so the
coordinator endpoint and worker instructions remain visible. The runner is prepared once on each
worker; the underlying process lifetime depends on the selected runner. The API does not call a
reset hook.

## Verification and limits

- Twelve focused tests cover authenticated coordinator/worker invocation, app-spec mismatch,
  effect-state protection, expired/late-lease handling, worker re-registration, full-worker-loss
  handling, bounded oversized-result reporting, coordinator-owned full-run persistence,
  worker-mode dry-run configuration, remote config-path instructions, and missing-token refusal.
- The full-run test uses an in-process worker client to exercise the real HTTP API; it does not
  benchmark cross-host latency, TLS deployment, throughput, or large capture transfers.
- The API uses bounded request scheduling and payload sizes, but cluster scale and failure rates
  remain unmeasured. If every worker disappears after startup, pending unleased invocations fail
  as not dispatched after the configured reconnect timeout. Oversized worker results are reduced
  to bounded request-limit outcomes without terminating the worker. G22's cases are still
  compiled and retained in coordinator memory.
- Reset-aware scheduling, worker health UI, pool autoscaling, open-loop/ramping load, and
  multimodal evaluators remain separate work.
