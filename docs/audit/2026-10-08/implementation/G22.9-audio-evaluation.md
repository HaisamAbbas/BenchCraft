# G22.9: bounded audio task evaluation

`deepeval.audio_g_eval@1.0.0` scores a recorded text or generated-audio response against one
inline audio case, task prompt, and reviewed reference answer. It runs in the isolated DeepEval
plugin worker and sends labeled audio input parts to an explicitly configured,
audio-capable OpenAI-compatible Chat Completions judge.

## Contract and limits

Case input contains an `audio` object with exactly `mime_type` and `data_base64`. Application
output may be a bounded text string or the same inline object shape. The evaluator accepts
PCM/IEEE-float RIFF/WAVE or MPEG Layer III audio only, verifies RIFF chunk sizes, format and
byte-rate fields, block alignment, and one complete MP3 frame, and limits each decoded audio
object to 4 MiB. It refuses URLs, paths, extra fields, other codecs, malformed payloads, and
oversized audio before making a judge request. WAV chunk traversal is limited to 64 chunks.

The 4 MiB evaluator limit is not the normal ingestion or HTTP transport limit. Dataset JSONL
lines are capped at 1,000,000 bytes including JSON/base64 overhead; case audio loaded that way
must remain below roughly 750 KB decoded. HTTP application request and response limits default
to 1 MiB. To return the maximum generated audio, configure `transport.max_response_bytes` to at
least 8,388,608. No timestamped transcripts, diarization, interruption, multi-turn voice,
video, or DeepEval upstream audio/multimodal metrics are included.

Audio, prompt text, the reviewed reference, and application output go to the configured judge.
The adapter reports provider token usage when present, never guesses cost, bounds judge replies
to 1 MiB, and does not follow redirects. It makes no live provider call in its tests.

## Verification

- The HTTP integration test carried a generated WAV through application JSON, output-pointer
  selection, durable execution storage, and the isolated evaluator worker into a local judge
  stub. It also checked bounded text output and that remote output and malformed case audio did
  not make judge requests.
- The final audio module passed 3 tests after WAV/MP3 hardening. Coverage includes plugin
  discovery and manifest identity, case/output limits, malformed RIFF metadata, WAV/MP3
  signatures and complete frames, labeled input/output request parts, token usage, and secret
  omission from the sanitized score artifact.
- The combined audio, vision, and DeepEval metric regression run passed 53 tests before the
  final audio-decoder hardening; the final audio-only rerun passed after those changes.
- Ruff and formatting passed for changed Python files; Mypy passed for `audio.py`; audit CSV
  and JSON files parse; `git diff --check` passed.
- Independent review findings on WAV field consistency and practical size limits were resolved.
  The final review found only the audit closeout bookkeeping gap, which this note and the ledger
  update resolve; see [G22.9 review](G22.9-audio-evaluation-review.md).

## Evidence boundary

The protocol body was verified against a local OpenAI-compatible fixture. A live provider/model
was not contacted; an endpoint that accepts Chat Completions must also support the `input_audio`
content part and the selected WAV/MP3 encoding. Judge scores remain provider-dependent.
