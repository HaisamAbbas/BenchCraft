# G22.10: timestamped sampled-video evaluation

`deepeval.video_frames_g_eval@1.0.0` scores a recorded text or sampled-frame response against
ordered image samples, the task prompt, and the reviewed reference answer. It runs in the
isolated DeepEval plugin worker and sends labeled inline image parts to the configured
OpenAI-compatible vision judge.

## Contract and limits

Case input contains `video.frames`, an array of 2 to 8 objects with exactly `timestamp_ms` and
`image`. Timestamps are non-boolean integers from 0 to 24 hours and must be strictly
increasing. Each image has exactly `mime_type` and `data_base64`, with a signature-checked PNG,
JPEG, or WebP payload. The complete case sequence is capped at 512 KiB decoded so it fits under
the built-in dataset readers' 1,000,000-byte row ceiling alongside prompt, reference, and other
fields.

Application output may be bounded text or an object containing only `frames` in the same
timestamped shape. Generated output allows at most 1 MiB per frame and 4 MiB per sequence. The
HTTP transport defaults to 1 MiB; configure `transport.max_response_bytes` to at least
8,388,608 for maximum generated-frame output. Raw video containers, URLs, paths, audio tracks,
and motion between supplied samples are unsupported. The judge is instructed to assess only
the supplied samples; it receives the timestamps in both a summary and frame labels, while
image parts retain the supplied order.

## Verification

- The focused video-frame suite exercises metric discovery, strict schema/timestamp/MIME/image
  limits, per-frame and aggregate input/output bounds, and HTTPRunner output selection through
  durable execution storage into an isolated worker and local judge fixture.
- The judge fixture verified chronological image-part ordering, timestamp labels, cost/token
  accounting, secret omission from score artifacts, and no judge call for malformed timelines
  or remote-image output.
- Existing audio, vision, and DeepEval manifest discovery tests passed after the plugin version
  bump to `0.2.0rc19`.
- Ruff and formatting passed for the changed source and tests; Mypy passed for
  `video_frames.py`; `git diff --check` passed.
- No live judge/provider call was made. The configured endpoint and selected vision model must
  accept multiple image parts.

## Evidence boundary

This is sampled-frame task scoring. It does not decode video files, evaluate continuous motion,
or validate that the supplied sampling strategy captures every event of interest. Scores remain
dependent on the configured judge, rubric, and frame selection.
