# G22.1 — Batched run work-item persistence

## Change

Run creation now writes work-item rows in bounded batches of 500 instead of committing each
row in its own SQLite transaction. Batch writes remain atomic and resumable: identical retries
are no-ops, changed content under a reused work-item ID is a conflict, and duplicate logical task
keys still fail the database uniqueness constraint. A failed batch rolls back completely. Run
creation can replay already-committed batches after interruption.

This addresses one measured local cost before work proceeds toward remote distribution. It does
not page the engine's in-memory queues, reduce the full dataset held during compilation, or add
workers/coordinator services.

## Verification

- Repository transaction tests: 35 passed, including identical retry, content conflict rollback,
  and duplicate-task-key rollback.
- Repository, engine and CLI run integration batch: 83 passed.
- File-backed process-kill recovery test: 1 passed; reopening SQLite after termination inside a
  batch recovered with neither partial row visible.
- Expanded storage/engine/CLI regression batch: 91 passed; one pre-existing example-plan CLI
  test failed once because the application's Git identity changed during that combined run.
  Rerunning that assertion alone passed (1 passed); no code change was made for it.
- `ruff check` passed for the changed files; `mypy --platform win32 src` passed for 168 files.
- A one-off file-backed SQLite microbenchmark on Windows 11 / Python 3.12.10 wrote 1,000 rows in
  0.602 s using one transaction per row and 0.022 s using batches of 500 (about 27 times faster
  for this isolated insert workload). This is a local storage microbenchmark, not end-to-end CLI
  capacity evidence.

## Review boundary

The change preserves the existing single-writer SQLite design. It does not provide distributed
execution, bounded in-memory scheduling, an offered-load profile, multimodal evaluation, or a
dashboard; those remain separate G22 work. No remote or cloud resources were provisioned.
The independent review found no code findings. File-backed process-level replay of a complete
compiled graph after termination between committed batches remains untested; see the
[independent review note](G22.1-work-item-batches-review.md).
