# G22.7 — Opt-in remote-worker measurement probe

G22.3's original measurement harness only exercised loopback workers launched by the
coordinator process. The opt-in `--remote-worker` mode adds a path for a host operator to
measure an independently started CLI worker over the coordinator API. It does not manufacture
cross-host evidence: the worker host must be supplied and operated separately.

## Running the probe

On the coordinator host, provide the worker bearer token through an environment variable backed
by the operator's secret manager. Do not pass the token as an argument. Supply a non-loopback
bind address, a reachable DNS name or IP in an HTTPS origin, a matching TLS certificate/key,
and a new path where the script can write the worker app config. The advertise URL must include
the same explicit port as the listening port. Ensure host firewall rules allow the remote
worker to reach that port.

For example, after setting `AIBENCH_WORKER_TOKEN` using the host's secret manager:

```text
uv run python scripts/measure_distributed_workers.py --remote-worker \
  --cases 100 --capacity 4 --rate 100 --burst 20 --delay 0.02 \
  --coordinator-listen-host 0.0.0.0 --coordinator-listen-port 8765 \
  --coordinator-advertise-url https://bench.example:8765 \
  --coordinator-tls-cert coordinator.crt --coordinator-tls-key coordinator.key \
  --worker-app-config-out worker-app.json --out remote-worker-measurement.json
```

The script prints the generated config path, the synthetic fixture command for each worker host,
and POSIX-shell and PowerShell worker commands. Copy the config to each host, start the fixture
so it listens on each worker's loopback port 8770, set the same token in each host's secret
manager, and launch at least the requested number of workers. The printed command includes the
selected `--token-env`; for a private certificate, use `--worker-ca-bundle-on-worker` to include
the worker-local CA path. The worker runs only the application runner and does not open or share
the coordinator's SQLite workspace. After the measurement result is written, stop each worker
with Ctrl+C or its service manager; worker clients retry while the coordinator is unavailable.

## Output and boundaries

The output records coordinator machine details, the minimum requested worker count, distinct
worker IDs seen, each ID's latest registered capacity, invocation outcomes, and
coordinator-observed latency percentiles. The count is a minimum: the coordinator API can accept
additional workers, so use a dedicated token and endpoint and do not register unrelated workers
during the measurement. Registration events do not prove that every worker was active or
contributed for the whole interval. HTTP 429 counts and worker-side workspace state are `null`
because the coordinator cannot observe them. `host_separation` is recorded as operator-selected
and not independently verified. The test suite intentionally uses local subprocesses and makes
no cross-host claim.

Remote mode requires HTTPS and TLS for the non-loopback coordinator listener and refuses
loopback, unspecified, broadcast, multicast, and `.localhost` advertise hosts, mismatched or
implicit ports, invalid token environment-variable names, and an existing app-config output
path. The generated app config is opened exclusively and contains no bearer token. Case count is
capped at 1,000; minimum worker count and per-worker capacity at 64; the total measurement
deadline is capped at one hour and worker startup timeout cannot exceed it. The fixture's HTTP
timeout exceeds its configured response delay. The synthetic fixture is a plain HTTP service
bound to worker loopback, not a production application. Preflight also caps the requested worker
HTTP client pool budget at the coordinator's 128 active API connections; each worker reserves
`capacity + 4` client connections. The report includes the pool budget implied by registered
workers, since unrequested extra workers can still connect and exceed that limit.

The probe includes worker polling, API round trips, coordinator scheduling, and calls to the
synthetic app. It excludes SQLite commits, evaluation, full CLI run overhead, and real provider
quota behavior. A real cross-host run remains pending until an operator has a separate worker
host and can save the resulting JSON evidence.

The implementation is reviewed in the [G22.7 review note](G22.7-remote-worker-probe-review.md).
