# G22.2 — Bounded run-work scheduling

## Change

Run creation already persists work items in bounded atomic batches (G22.1). The engine now also
pages pending execution work in 500-item batches instead of decoding and retaining the entire
work graph at startup. Ready evaluations are selected from SQLite in bounded pages only after
their execution dependency reaches a terminal state. A row cursor wraps so evaluations made
ready by later execution completions are still discovered.

Execution recovery and run-case validation stream work-item rows in bounded batches, and run
progress counts come from SQL aggregates. The engine loads the latest execution attempt and
previous execution states lazily; its two lookup caches are limited to 500 entries each.

Retries remain bounded as well. Evaluation reservations account for queued, quota-held, delayed,
and in-flight work. Retry promotion can join a prefetched page without exceeding the 1,000-item
retry buffer, and a throttled evaluator cannot consume the scan budget needed by another evaluator.
Graceful interrupts leave unstarted work pending for resume rather than refilling and spinning.

This bounds scheduler and work-record memory, not total run memory: compilation and the case map
still hold the run's cases in memory. No large-scale end-to-end memory or throughput claim is made.
The chosen future distributed-worker architecture remains a coordinator API with workers that do
not share a SQLite workspace.
