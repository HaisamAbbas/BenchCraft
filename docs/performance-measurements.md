# Performance measurements

Run reports and run comparisons separate successful request latency, retry-inclusive request time, throughput, and warmup observations. Application attempts are read from the run database; rendering or comparing reports does not invoke the application.

The `application.latency` summary describes final successful, uncached measurement attempts. It includes nearest-rank p50, p75, p95, and p99, arithmetic mean, minimum and maximum, population standard deviation, interquartile range (p75 minus p25), and coefficient of variation. Nearest-rank percentiles return observed samples, so with small samples p95 and p99 often equal the maximum. Failed, timed-out, cached, and warmup attempts do not enter these latency statistics; their counts or phase summaries remain visible separately. Missing or invalid measurements are counted rather than treated as zero.

`application.latency.retry_inclusive` summarizes successful measured requests from the start of the first dispatched attempt through completion of the final attempt. It includes retry delays and time between resumed sessions. It needs valid timestamps on the relevant attempts; if an earlier attempt was dispatched but its result was lost, that request is marked as missing instead of reporting a shorter lifecycle time. When a recovered dispatch cannot be assigned to a phase, the retry-inclusive phase summaries are marked incomplete and emit no samples.

`application.latency.throughput` reports successful final measured requests per second over the observed measurement phase, from the first committed dispatch start to the last final completion. Concurrent requests share that wall-clock interval, and retries extend it. The summary reports its request count, attempt count, duration, and missing timestamps. Throughput is `null` when timestamps are incomplete, an uncommitted dispatch makes the interval uncertain, or a recovered dispatch cannot be assigned to either phase. The last case also marks phase attribution incomplete without counting the dispatch in either phase. `warmup_throughput` uses the same definition for the warmup phase.

`run.load_profile` freezes the selected scheduling mode. `closed_loop` (the default) starts work when an application concurrency slot is free. `open_loop` schedules first-attempt arrivals at `n / requests_per_second`; `ramp` schedules them by inverting the integrated linear rate from its starting to final rate, then holds the final rate after the configured ramp duration. The first measured arrival is at offset zero. Warmups finish before the schedule starts. Retries use the normal retry policy and do not consume first-attempt arrivals. Execution caching is incompatible with open-loop and ramp profiles because cached outputs are not new application calls.

`application.latency.offered_load` reports planned first attempts, observed runner hand-offs, and nearest-rank dispatch-lag statistics. Lag runs from the scheduled offset to the local runner hand-off and includes any application reset performed before invocation. It excludes downstream worker queueing, network delay, and application-observed start time, so it must not be read as end-to-end request latency. If concurrency, reset work, quotas, or another scheduler limit prevents the target rate, the bounded queue delays later hand-offs and lag grows. Pause freezes active profile time. A resumed engine session starts a new profile clock at offset zero for remaining unstarted first attempts; interrupted intervals across sessions are therefore not a single continuous offered-load phase. A failed reset has no runner hand-off and leaves that planned arrival unobserved.

`application.latency.warmup` gives final-attempt latency statistics for successful, uncached warmups, separate from measurement latency. It identifies the harness phase and does not claim that every application's runtime or remote service was physically cold or warm. Comparisons expose the same statistics under each run's `application_performance` entry; the existing `latency_p95_ms` field remains the p95 used by current regression policies.

For an OpenAI-compatible application, set `transport.parameters.stream` to `true` to request server-sent events. BenchCraft asks for `stream_options.include_usage` by default so the endpoint can report completion tokens; set it to `false` if the provider does not support usage chunks, in which case output tokens per second stays unavailable.

Streaming summaries are recorded under `application.latency.streaming` and `application.latency.warmup_streaming`, with matching per-run fields in comparisons. TTFT runs from the start of the benchmark request to the first non-empty content delta. Inter-token observations are client receive-time gaps between non-empty content deltas; providers may combine several tokenizer tokens in a delta, and network buffering can deliver several deltas together. The overall mean weights all summarized gaps; p50 and p95 summaries describe per-request means and per-request p95 values. At most 100,000 intervals per response are retained for summary statistics, and truncation is reported.

Output tokens per second uses the endpoint's `usage.completion_tokens` divided by elapsed time from the first content delta through the `[DONE]` marker. It is unavailable without reported usage, a positive generation interval, or a complete stream. Integrity requires a `[DONE]` marker, all expected choices and finish reasons, and no malformed events. An incomplete stream becomes an application error; any observed TTFT and content-delta gaps remain available for diagnostics.
