# ADR 0011: MVP acceptance and harness validation

Status: Accepted
Date: 2026-09-24
Prompt: 12 — MVP acceptance and harness validation

## Context

§17 defines MVP acceptance: a 100-case run with an injected RAG failure, a black-box missing-evidence warning, resume and rescore, plus a conversational journey. §23 asks for:
- a versioned planner fixture set compared against a template baseline;
- judge calibration;
- invariant, fault and workload checks;
- results reported against targets without relabelling them as passes.

This prompt must also not treat synthetic execution as human review or live trials.

## Decisions

### Acceptance fixture (12-T1)

- **The fixture.** `examples/acceptance/` holds a standard-library HTTP RAG service (`rag_service.py`) and a generated 100-case dataset (`rag100.jsonl`, regenerated by `make_dataset.py`). The generator verifies every case against the service's own retrieval.
  - Eight cases carry a decoy word that pulls retrieval to the wrong document. They are marked `metadata.injected = "retrieval_failure"`.
  - `/blackbox` returns answers without retrieval.
  - The service counts calls per question, so a test can prove that resume and rescore do not call the application again.
- **The tests** (`tests/test_mvp_acceptance.py`) run the service inside the test process, so its counter outlives an engine child process that the test kills. The conversational journey uses the scripted provider: it proves the harness side, not a live model.
- **Evidence command.** `examples/acceptance/run_acceptance.py` runs the same workflow through the installed CLI. It writes a summary covering reliability (successful executions and completed evaluations over their eligible counts, with an error taxonomy), cost accounting completeness, per-case call counts, injected-failure detection and rescore calls. The results are kept in `docs/engineering/evidence/12/`.

### Planner fixture set (12-T2)

- **Format and command.** `benchmarks/planner/v1/fixtures.json` (schema `aibench.planner-fixtures/1`) holds a manifest-only catalog, named policies and 40 fixtures. `aibench plan benchmark` loads it (`planning/benchmark.load_fixture_set`) and runs any planner function over it (`run_fixture_set`). It never contacts an application and never evaluates anything.
- Fixture IDs are labels only. Per-fixture scratch directories use generated names, so an ID from an external fixture set cannot escape the temporary directory.
- **Annotations are concept-level.** Each fixture lists concepts to select or report as gaps, `forbidden` evaluator IDs, and whether the plan must be refused. The format also supports `acceptable` extra concepts, but no v1 fixture uses them yet. The result is reported with fractions and Wilson 95% intervals, per family and split into development and held-out families. It is compared with the §23 targets as met, not met, or not measured.
- **Held-out rule.** Held-out families are not used to change the planner. A held-out fixture whose measurement is used to fix a defect is moved to development, with a note. This happened once, to `retriever_disabled_runtime`.
- **Review status is recorded, not assumed.** The annotations were written by the implementing agent. `reviewers` is empty, and every report states "unverified: no fixture has been reviewed". §23's two human reviewers with adjudication are pending.
- **Targets are not relabelled.** The template baseline misses the recall target (17/21 against 0.85). The report says "not met". `--require-targets` exits 1 in that case, for use as a release gate.
- **The model planner is measurable but not measured.** `--planner model --provider-config` runs under the same policy gate as `aibench plan`. It was not run, because no live provider is authorized.

### Judge calibration (12-T3)

- **Format.** `benchmarks/judges/v1` (schema `aibench.judge-calibration/1`) holds 33 labelled cases across correct, formatting, paraphrase, verbose, subtly wrong, incomplete, wrong, adversarial, unanswerable and non-text outputs.
- **Command.** `aibench evaluators calibrate` (`services/calibration.py`) runs each case twice with the in-process native evaluators. It reports agreement, false acceptance, false rejection and repeat stability per binding and category, with undecided cases kept separate.
- **Unmeasured judges are listed.** Model judges appear under `not_measured` with the reason. The labels are unreviewed.
- **Invariants.** A seeded randomized test (600 generated cases through the real scorer, with an evaluator that misbehaves on purpose) checks that evaluation never mutates a Golden, that an error or not-applicable result carries no score, and that the decision follows the frozen rule. It also asserts that every branch occurred. It is property-style, without adding a dependency.
- **Workload.** A 1,000-case workload test is opt-in (`AIBENCH_WORKLOAD_TESTS=1`, about 4 minutes). It checks resume, per-case call bounds and traced peak memory.

### Audit (12-T4)

- **The audit document.** `docs/engineering/mvp-acceptance.md` maps every §17 ship item, every §17 acceptance clause and every §23 validation area to a status and its evidence. The status values are Verified, Verified (manual / scripted model / Windows), Partial, Blocked and Not done.
- **The matrix.** Every row of `requirements-matrix.md` gains Status and Evidence columns. No blanket label hides a partial or blocked row.

## Defects fixed

1. **A declared but disabled retriever was still planned** (07-T2, §23). Recorded executions whose retrieved context is empty every time now mark the capability in `ApplicationProfile.always_empty`. The catalog makes an evaluator that needs that field non-empty ineligible, and says why. Before the fix, the fixture set measured precision 17/18 with 1 unsupported selection; after it, 17/17 and 0.
2. **Reports under-counted application calls after a crash** (11-T1, 11-G2). Calls in flight when a session died have no committed attempt. Recovery records them as `uncommitted_dispatches`, and the budget ledger counted them, but the report did not. The report now adds them to application calls, with unknown cost (104 in the acceptance run). The count is an upper bound on calls that actually reached the application (see Changes after independent review).

## Changes after independent review

An adversarial review with executed reproductions reproduced every number in the documents, and the acceptance tests passed 6 of 6 repeat runs. It confirmed 2 major and 7 minor findings. All are fixed, or corrected in the documents. Regression tests are in `tests/test_acceptance_review_regressions.py`.

- **Major:**
  1. **Fallback.** A model planner that fell back to the template was reported as a model result. The benchmark now counts fallbacks and warns. If any executable fixture fell back, every target reads "not measured".
  2. **Unrun invariant branches.** The invariant test never reached its error branch. It now drives the real scorer with an erratic evaluator and asserts that pass, fail, error, not-applicable and skipped all occur.
- **Minor:**
  - **Uncommitted count.** It is an upper bound, not exact. The test asserts bounds, and the documents say so.
  - **`always_empty`** needs at least 3 observations, all empty.
  - **Reliability** is split into executions and evaluations over their eligible denominators.
  - **Unsupported selections** include any ineligible catalog option.
  - **Rejections** must cite a missing permission.
  - **Malformed fixture or calibration sets** are refused with a clear error.
  - **Documents.** The unsupported `acceptable` claim is corrected. Workload and profile outputs are saved under `evidence/12`. The matrix status now matches the phase status.
- **Follow-up review:** fixture IDs were joined directly to the temporary directory path; an absolute ID could write `app.json` and `data.jsonl` elsewhere. Scratch directories now use generated names. The fixture and calibration loaders also reject malformed nested values with domain errors instead of tracebacks.
- **Recorded rather than changed:**
  - **Annotation doubts** (`image_captions`, `structured_extraction`, `budget_objective`, security fixtures annotating a metric) are left for human review, because changing annotations after measurement would move the goalposts.
  - **Self-assigned concepts.** Gap and unnecessary-evaluator scoring rely on the concepts the planner assigns itself.
  - **Crash window.** A crash between recovery and its event can lose uncommitted dispatches.

## Consequences and limits

- **Profile schema.** `ApplicationProfile` gains `always_empty`, defaulting to empty. Older profiles load unchanged. Every profile hash changes, because the field is part of the dump. Profile hashes are recorded, never compared.
- **Throughput.** Measured: 1,000 cases in 152.6 s (closeout run) and 233 s (development run) at concurrency 16. Profiling 200 cases (`evidence/12/engine-profile-200.txt`: 28.6 s, 7.0 cases/s) shows almost no CPU time. Each call waits on a new HTTP connection being set up and torn down, and on its capture artifacts being written, fsynced and read back for verification (`artifacts.write_bytes`, `commit_verified_artifact`). Cumulative profile times overlap across concurrent tasks, so this shows where calls wait, not an exact breakdown. This is recorded, not changed: durability comes first, and it is a scale-work item.
- **Still open for release (Prompt 13), and not hidden:**
  - the recall target;
  - human review of fixtures and labels;
  - live judge, model planner and conversation trials;
  - Linux, macOS and Python 3.11 runs;
  - disk-full testing;
  - terminal resizing.
