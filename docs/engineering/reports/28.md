# Prompt 28 — Optional black-box HTTP evaluation

Status: **COMPLETE for the existing, configured JSON HTTP API contract.** The user explicitly
started this optional phase by submitting Prompt 28. The contract was already implemented in

did not add a second HTTP runner. Generic URL discovery and browser automation remain deferred.

## 1. Implemented functionality and changed files

No runtime changes were needed. The existing implementation provides the bounded contract:

- `HttpTransport` is a configured JSON API transport. It supports `POST`/`PUT` request
  methods, typed request headers, secret-reference headers, TLS settings, explicit endpoint
  allowlists, controlled method-preserving redirects, request/response byte limits, connect
  and total timeouts, correlation IDs, and optional health/reset hooks.
- `InputBinding` uses JSON Pointers to project app-visible case fields into a request template.
  `OutputBinding` maps JSON response fields to the answer and optional retrieved context, tool
  events, usage, cost and world state. Unbound or missing observations remain unknown; the
  output-only black-box fixture therefore receives a coverage gap instead of an invented
  groundedness score.
- Secret values resolve only from configured secret references allowed by policy. Captured
  request/response material, sensitive response headers and echoed secrets pass through the
  redactor. Judge-only references are excluded by the shared input projection.
- The existing execution policy validates the application, effect level, HTTP origins and
  secret references before dispatch. `EndpointPolicy` checks the target and every redirect
  hop. TLS verification is enabled by default and environment proxies are ignored.
- The shared engine supplies plan-configured application concurrency and request-rate quotas,
  bounded backpressure, call/wall/cost budgets, cancellation and effect-aware retry policy.
  The HTTP runner never retries by itself. Dispatch before a response records an unknown
  effect; failures before dispatch record no dispatch; observed response and gateway states
  preserve their documented semantics.
- The local acceptance HTTP service is exercised through the shared chat, session, run,
  evidence and report path by clean-installed E2E-01. No live endpoint is contacted.

The implementation paths are `src/aibench/core/models.py`,

## 4. Decisions and scope limits

- Prompt 24 had already identified the tested HTTP runner and placed HTTP transports in the
  v1.1 MVP. This phase closes the narrow configured API requirement by reusing the existing
  implementation and adding executed evidence to `docs/engineering/product-alignment-v4.md`.
- “Black-box” means an API whose declared response exposes only some observations. Missing
  retrieval/tool/usage/cost observations stay unavailable; there is no automatic inference
  from source code or arbitrary website behavior.
- Only configured `POST`/`PUT` JSON APIs are evaluation targets. `GET` is used for optional
  health checks. Live targets require a configured application plus policy-approved origins,
  effects and secret references. No external network call was made in this phase.
- Rate limiting is plan-configured through shared application quotas; it is not a guessed
  provider limit. Application cost caps are soft estimates because an endpoint may not report
  cost; actual unknown cost is never treated as zero.
- No new ADR was needed. The v4 broad website/browser claim stays deferred under V4-17; the
  old ticket/test/report discipline remains active.
