- **22-T3: a deterministic vertical suite from a clean environment.**
  - **The conversational loop in the installed CLI** (new):
    - `examples/e2e/scripted_assistant.py` is a deterministic OpenAI-compatible assistant
      stand-in. It speaks JSON and streaming, replays a scripted sequence of tool calls
      and fills their arguments from the actual tool results. An extra call gets HTTP 500.
    - `tests/test_e2e_cli_journey.py` runs `aibench chat` in a real Windows ConPTY
      against the HTTP RAG fixture. The flow is: first natural-language message → one
      clarification → a revised 20-case draft → "Run it." → a question mid-run → `/pause`
      (no new dispatch) → `/resume` → an evidence-grounded failure discussion →
      `/report` → exit, reopen and `/status`.
    - The results are then read back through `sessions list`, `runs list`, `report` and
      `chat --send /failures`.
  - **The suite runner** (new): `scripts/e2e_suite.py` builds the sdist and the wheel,
    installs the wheel into a clean venv constrained by the lock file, checks that
    `aibench` imports from site-packages, runs the tests for each journey, and writes
    `e2e-suite.json`.
  - **Defect fixed (in scope, core loop):** a pause requested while a run was starting was
    honoured, since nothing dispatched, but the committed status stayed `running` until
    start-up ended. So `/status` contradicted `/pause`, against §15: "show `pausing` until
    it reaches a safe boundary".
    - **Symptom:** it appeared as an intermittent failure of the Prompt 12 acceptance
      journey, 1 in 6 runs in the clean venv.
    - **Fix:** `RunEngine._while_starting` awaits runner preparation and evaluator
      start-up while watching for control changes, and `RunController.next_change` supports
      that (`src/aibench/engine/engine.py`).
    - **Regression test:**
      `tests/test_engine.py::test_a_pause_while_the_run_is_starting_is_committed_as_pausing_at_once`.
      It fails without the fix (`('running', 0)`) and passes with it.
    - **Side effect:** Ruff's formatter reflowed one long condition in `engine.py`. That
      change is formatting only.
- **22-T4: safety and reproducibility.** E2E-03 to E2E-07 check, with side-effect counters:
  - denial makes zero calls;
  - references stay isolated from the application and the assistant;
  - missing evidence is a gap, not a score;

- **22-T5: value audit.** Every row has a value class. The judgement is in §4. No code was

4. Decisions or specification discrepancies recorded

- **Discrepancy: E2E-01–07 are undefined in the repository.** The repository's prompt pack
  (v1.0) has no Prompt 22 and no E2E-01–07.
  - **Decision:** the journeys were derived from Prompt 22's text and the §17 acceptance
    clauses, and are recorded in the matrix.
  - **Impact:** if the newer pack defines them differently, re-map the journey table. The
    tests themselves stand.
- **Is this a usable benchmark-focused Hermes/Codex experience today?** Partly: yes for the
  loop, not yet as an agent that reasons about evaluation.
  - **Proven, from a clean install, through the real CLI.** A user can state a goal in
    plain language and get:
    - a focused clarifying question;
    - a revised plan;
    - a run started only on explicit consent;
    - answers while the run is live;
    - pause and resume;
    - an explanation of failures grounded in stored evidence, with every number traced to
      a query;
    - a report;
    - reopening with no repeated calls.

    Persistent sessions, turn handling, typed and policy-checked tools, interruption and
    steering, durable run state, and inspect → execute → verify all work.
    Proof: `test_e2e_cli_journey` and E2E-02–07.
  - **Not proven.**
    - Every conversational check uses a scripted model. How a real model uses these tools
      has never been observed.
    - Inside chat, the plan is drafted by the deterministic template. The assistant only
      steers it through typed patches. The bounded LLM planner is reachable only through
      `aibench plan`.
    - So the "agent reasons about what to evaluate" part of the differentiator is thin
      today: it is keyword and template mapping, with 17/21 planner recall.
- **Overbuilding (recommendations, and user decisions; nothing was removed).**
  - **Merge candidates.**
    - `score` and `evaluate`: two rescoring commands.
    - `benchmark` and `chat --send`.
    - `app smoke` into a one-case engine run.
    - The two planner fixture sets.
    - The two negation heuristics.
    - 14-T4, 18-T3 and `17-P18` into their parent tickets.
  - **Candidate for removal:** the 17-T1 openai/evals OSS bridge. Its allowlist duplicates
    native exact-match checks, and it adds a separate run type. No demand is recorded.
  - **Defer.** Most of Prompts 16–19 are headless-only and can't be reached from the
    conversation:
    - source inspection, traces and caches;
    - candidates and episodes;
    - the hosted Evals API bridge and Langfuse;
    - controlled experiments.

    The Ragas adapter adds only a second faithfulness metric. It is optional and labelled,
    but it does not advance benchmark-specific conversational use now.
- **Recommended slim core:** the conversational loop; local, CLI and HTTP runners;
  validated native and DeepEval evaluators; the deterministic run engine with policy,
  budgets and recovery; persistent evidence, reports and rescoring; plus the E2E suite.
- **Missing interaction behaviour:**
  - chat cannot use the model planner;
  - chat drafts cannot declare release gates (report 11);
  - Phase 2/3 capabilities are not reachable through `PlanPatch` or slash commands.
- **Ledger corrections** are added as dated notes in `tickets.md` for 05-T1, 11-T3, 07-T3,
  02-T2 and the Prompt 17 status. The original rows are kept.
- **Orphaned guard, not changed:** `assert_no_policy_keys_from_dataset` has no production
  caller. Policy is loaded from separate files, so datasets cannot supply it today. The
  guard should be wired in or retired, as a separate ticket.
