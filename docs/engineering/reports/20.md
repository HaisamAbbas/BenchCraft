Phase 20 — Distributed execution after measured need
Status: DEFERRED

20-T1's optional-scope condition applies. The local bottleneck was measured and is real,
but no distribution need was demonstrated. No distributed component is implemented or
claimed. The decision is recorded in ADR 0019.

1. Implemented functionality and changed files

- **20-T1: measure the need, and define the contracts.**
  - **Measurement driver.** `scripts/measure_capacity.py` (new) runs the real
    `aibench run --json` CLI in a fresh project per scenario. It runs against
    `examples/apps/rate_limited_app.py`, served in-process with a quota far above the
    offered load, and the app's response delay stands in for application latency. For
    each scenario it records:
    - throughput, the engine's elapsed time and the process wall time;
    - process-tree CPU and peak memory. On Windows, a job object covers the venv launcher
      and the interpreter; the process starts suspended and every Win32 call is checked.
      On POSIX, `os.wait4` measures each child;
    - system CPU load;
    - peak in-flight requests and arrivals seen by the server;
    - workspace database and artifact bytes;
    - its own command line.
  - **Evidence** (new): `docs/engineering/evidence/20/`, containing `capacity.json`,
    `capacity-3000.json`, `profile-300-c64.txt` and a `README.md` giving the exact
    commands.
  - **Contracts and decision.** ADR 0019 (new) records:
    - the target workload that would justify distribution: a declared real workload, the
      harness as the binding constraint, and a deadline that can't be met locally;
    - the resource budget;
    - the failure model a coordinator must survive: duplicate delivery, lease expiry and
      fencing, worker or host death, partial uploads, an unavailable coordinator,
      pause and cancel under failure, and no exactly-once external effects;
    - the conditions for reopening.
- **20-T2 and 20-T3: DEFERRED.** No PostgreSQL coordinator, durable queue, object store,

4. Decisions or specification discrepancies recorded

- **ADR 0019: distributed execution is DEFERRED.**
  - **The shortfall is real.**
    - One harness process delivers about 18–23 cases/s at concurrency 16–64, and 14 of the
      64 cases/s a 1 s application at concurrency 64 would allow.
    - Memory grows about 46 KiB per case, about 44 GiB at a million cases, extrapolated.
    - The spec's §15 million-case illustration is not achievable on one host today.
  - **Why it's still deferred.**
    - No declared workload depends on closing the shortfall.
    - Cheaper single-host levers that target the measured costs are untried: group commit,
      bounded work-item batches (already required by §15), and several engine processes
      on one host.
    - Distribution would parallelize the same per-case cost, plus a round trip to the
      coordinator for each commit.
  - **Reopening** needs a declared workload that still misses its deadline after those
    levers.
- **Recommended next local step (not started).** Bounded work-item batches and group
  commit, as their own ticket with crash-recovery tests. Then re-measure with
  `scripts/measure_capacity.py`.
- **Predecessor discrepancy.** When this prompt started, `phase-status.md` marked Prompt
  19 COMPLETE, but `docs/engineering/reports/19.md` did not exist; another session was
  still finishing it. The report exists as of this closeout. Prompt 20's deferred outcome
  does not build on Prompt 19's contracts.
- **Concurrency.** ADR 0018 and migration 11 belong to Prompt 19. Prompt 20 uses ADR 0019
  and adds no migration.
