## 2. Closed implementation gaps

- **Fresh repository-aware conversation (30-T1).** The existing `CodebaseInspector` now feeds
  the shared application profile when session policy approves the project root. The profile
  keeps path/line evidence and inferred/unknown states. The fresh-chat E2E refuses source-text
  authorization, omits a secret sentinel, runs the validated app, stores evidence/report,
  reopens the session, then rescores with no new application calls.
- **Bounded no-repository HTTP setup (31-T1).** `aibench connect http` validates a user-chosen
  local JSONL file and emits typed application/policy/project configuration without contacting
  the endpoint. Remote HTTPS requires exact-origin authorization; auth values are references,
  not literals; request effects and a call ceiling are declared. Setup refuses overwrites.
- **Hybrid local evidence continuity (31-T2).** One configured HTTP session/run receives a
  manually imported OpenTelemetry trace summary and approved repository findings. The test
  observes the same run ID and one loopback app request; raw trace files and secret contents
  are not passed to the assistant.
- **Conversational controlled experiments (31-T3).** A typed tool reuses the existing frozen
  experiment service. It requires exact user authorization, app-declared finite parameter
  values, a named holdout inside approved data roots and bounded trial/call budgets. Progress
  is read from storage; a stored running experiment resumes its existing trial IDs; protected
  holdout scoring is a separate explicit action. No source edits or automatic adoption occur.
- **Recovery status correction.** `SessionController.start_experiment` now reports a resumed
  state when it continues a stored `RUNNING` record. A conversation test simulates restart
  after durable start and verifies completion using the stored trial identities.

## 5. Remaining limitations

- General website/browser automation, arbitrary URL discovery, and broad live API onboarding
  remain deferred. `connect http` writes a specific configuration; it does not inspect an API.
- Historical production logs are not automatically imported or selected. A local JSONL source
  and explicit existing connectors remain the supported paths.
- Repository language/framework and metric discovery remain narrow; unsupported patterns are
  reported as unknown/unavailable.
- Real-model planning and judge quality, human label review, real-agent operation, usability,
  willingness to pay, time saved, pilot results and product-market fit are unvalidated.
- The package version remains `0.1.0rc1`; this acceptance run verifies a local wheel, not a
  public release artifact or multi-platform release.

No API key was needed for this work. A provider secret and cost authorization are only needed
for an optional live-model/judge smoke test, which is outside this deterministic completion.

## 6. Product value review

### Verified implementation

The verified product loop now joins bounded repository evidence, evidence-aware opportunities,
a typed configured runner, a persistent conversation, stored trace/case evidence, reports and
controlled experiments. This claim is about the local test contract above.

### Sourced adjacent capabilities

Current official documentation describes substantial adjacent functionality:

- [LangSmith evaluation types](https://docs.langchain.com/langsmith/evaluation-types) document
  curated-dataset offline benchmarks, unit/regression evaluation, comparisons, production
  backtesting, and online evaluation modes.
- [Braintrust evaluation](https://www.braintrust.dev/docs/evaluate) documents dataset-backed
  offline experiments, immutable experiment records, CI/CD evaluation and production online
  scoring. Its [dataset documentation](https://www.braintrust.dev/docs/annotate/datasets)
  describes versioned datasets populated from production logs, feedback, manual curation and
  generated examples.
- [Arize Phoenix](https://arize.com/docs/phoenix/get-started) documents a tracing → evaluation
  → datasets → controlled experiments workflow; Phoenix supports OpenTelemetry/OpenInference
  tracing, as covered by its [official overview](https://arize.com/docs/phoenix/).

These official product sources establish documented capabilities, not a comparative test of
those products. No claim is made that conversational shells, adapters, repository inspection,
or this combined workflow is unique.

### Proposed differentiation and unvalidated hypotheses

Potential differentiation to test: local-first repository awareness connected to policy-bounded
execution and durable evidence in one conversational workflow. The hypothesis that this makes
evaluation setup materially easier for nontechnical users is unvalidated. Establish it with
observed task-completion sessions and pilots; do not infer adoption or product-market fit from
these deterministic tests.
