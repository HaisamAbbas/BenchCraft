1a. Review findings and remediation (this pass)

- **High — `commit_artifact` only compared `digest` for idempotency, not the full
  `ArtifactRef`.** A retry with the same `artifact_id` and `digest` but a different `uri`,
  `mime_type`, `size_bytes`, `redaction`, or `run_id` was silently accepted, potentially
  leaving stale/incorrect metadata committed. Fixed in `src/aibench/storage/migrations.py`
  (added an `artifacts.content_hash` column, hash of the complete `ArtifactRef` JSON,
  alongside the existing `digest` column which stays for its own indexed lookups) and
  `src/aibench/storage/repositories.py::Storage.commit_artifact` (now compares
  `content_hash`, so any field mismatch raises `ConflictError`). Covered by a parametrized
  test (`tests/test_storage_repositories.py
  ::test_commit_artifact_conflicts_on_metadata_mismatch_even_with_same_digest`) exercising a
  mismatch in each of `uri`/`mime_type`/`size_bytes`/`redaction`/`run_id` independently.
- **High — `ArtifactStore.read_bytes()` trusted `ArtifactRef.uri` directly, with no path
  validation or content verification.** Fixed in `src/aibench/storage/artifacts.py`:
  - `_resolve_and_validate_uri()` resolves the URI and rejects anything that does not fall
    inside `artifacts_dir` (a forged absolute path elsewhere, or a `..` traversal).
  - `verify_ref()` resolves the URI, then checks the file exists, its size matches
    `ref.size_bytes`, and its content hashes to `ref.digest` — raising `ValidationError` on
    any mismatch — and returns the verified bytes.
  - `read_bytes()` is now defined as `verify_ref()`, so every read is validated, not just
    digest-shaped path construction.
  - A new `commit_verified_artifact(store, storage, ref)` helper verifies a ref against the
    real file *before* it ever reaches `Storage.commit_artifact`, addressing "verify ...
    before committing or reading" directly — a forged ref (e.g. a claimed `size_bytes` that
    doesn't match the real file) now never reaches the database at all.
  - New tests in `tests/test_storage_artifacts.py`: a `uri` pointing outside `artifacts_dir`
    (both an absolute elsewhere-path and a `..` traversal) is rejected; a forged
    `size_bytes` is caught; a file tampered with after being written (bypassing the store's
    own write path, so its content no longer matches the committed digest) is caught on
    read; a missing file is caught; `commit_verified_artifact` accepts a genuine ref and
    rejects a forged one before any DB write happens.
- **Verification blocker — pytest temp-directory permission errors persisted in the
  reviewer's sandbox** despite Prompt 01's `tests/conftest.py` write-probe fallback logic.
  Rather than attempt a third variation of the same directory-selection trick (which cannot
  fix a sandbox that structurally disallows all filesystem writes available to that
  process — an environment property outside this repository's control, as recorded in
  Prompt 01's report), the fix here **shrinks how many tests need a temp directory at all**:
  `Database.open_in_memory()` (`src/aibench/storage/db.py`) opens a `:memory:` SQLite
  connection with migrations applied, no filesystem touched whatsoever.
  `tests/test_storage_repositories.py`'s `storage` fixture and four of
  `tests/test_storage_migrations.py`'s five connection-based tests now use it, since they
  test pure repository/migration logic and never needed a real file — only genuine
  restart-across-a-real-file tests
  (`test_reopening_database_reapplies_migrations_idempotently`) and genuine
  filesystem-persistence tests (`test_storage_artifacts.py`, `test_storage_recovery.py`,
  `test_cli_runs.py`) still use `tmp_path`. This cut tmp_path-dependent tests in this phase's
  new suite from 61 to 34 — a real reduction in exposure to that sandbox limitation, not a
  workaround. `AIBENCH_TEST_TMPDIR` remains documented for the tests that still need it.

1b. Second review and remediation

A second review confirmed §1a's fixes were substantively correct, then found two further
issues in how they were implemented:

- **High — the `artifacts.content_hash` column (and, on inspection, several other
  content_hash/manifest_hash columns from earlier remediation passes) had been added by
  editing `_0001_initial` directly**, instead of a new migration — contradicting this file's
  own stated policy ("Add new migrations by appending to `MIGRATIONS`; never edit an
  already-shipped one") and, concretely, meaning any database created before that edit would
  be missing the column and fail the next time `commit_artifact` tried to write it. Fixed by:
  - Reverting `_0001_initial` in `src/aibench/storage/migrations.py` to the schema it had
    before *any* reactive column additions (keeping only the `content_hash` columns that were
    part of the original, pre-review Prompt 02 design on `applications`/`plans`/`runs`/
    `execution_attempts`/`metric_results`).
  - Adding migration `_0003_content_hash_columns` (`ALTER TABLE ... ADD COLUMN`) for the
    `content_hash`/`manifest_hash` columns `work_items`, `datasets`, `cases`, `profiles`,
    `artifacts`, `usage_events`, and `approvals` had reactively gained across earlier
    remediation passes — fixing the same defect everywhere it existed, not just for the one
    table this review happened to flag.
  - Giving `Migration` an optional `post_apply(conn)` hook, run inside the *same* open
    transaction as the migration's SQL (via a `BEGIN`-prefixed `executescript` that
    deliberately omits the closing `COMMIT`, so a plain `conn.execute(...)` call afterward —
    including from Python logic — still participates in that transaction before an explicit
    final `COMMIT`), since backfilling the new columns' values from existing rows needs
    SHA-256 hashing SQLite has no builtin for.
  - `_0003`'s `post_apply` backfills every pre-existing row: for tables whose `data` column
    already holds the model's full canonical JSON (`cases`, `profiles`, `work_items`,
    `usage_events`, `approvals`), it hashes that string directly — exactly what a fresh
    commit of identical content computes, since `Storage`'s commit methods hash the
    already-serialized JSON string rather than re-serializing. `datasets` and `artifacts`
    (which store individual columns, not one JSON blob) are reconstructed into the
    corresponding core model and re-serialized the same way `commit_dataset`/
    `commit_artifact_unverified` do before hashing.
  - New test `tests/test_storage_migrations.py
    ::test_upgrading_a_pre_remediation_database_backfills_content_hash_columns` — the exact
    scenario the review asked for: applies only migrations 1–2, inserts legacy rows via raw
    SQL matching that pre-migration-3 schema (no `content_hash` column), then applies the
    full migration set and proves (a) it succeeds, (b) a subsequent identical commit of the
    legacy work item/artifact is correctly recognized as a no-op (not a false-positive
    `ConflictError`, which would happen if the backfilled hash didn't match what a fresh
    commit computes), and (c) a genuinely different work item/artifact under the same key is
    still correctly rejected — the backfill didn't make conflict detection permissive.
- **High — `Storage.commit_artifact` remained directly, publicly callable with no
  verification**, so a caller bypassing `commit_verified_artifact` (exactly what several of
  this phase's own tests did, with fake paths like `/x`) could still persist a forged
  reference — undermining 02-G3's "no committed result references a partial or nonexistent
  artifact" guarantee at the API level, even though the two building blocks (`verify_ref`,
  `commit_verified_artifact`) already existed from §1a. Fixed by renaming the method to
  `Storage.commit_artifact_unverified` (`src/aibench/storage/repositories.py`) with a
  docstring that states plainly it performs no filesystem check and that real callers must
  use `commit_verified_artifact` instead. This doesn't make misuse impossible (Python has no
  true private methods), but makes it visible at every call site — `git grep
  commit_artifact_unverified` now finds exactly the handful of DB-layer-only tests that
  intentionally use it, documented as such, and nothing else. All non-test-only production
  call sites go through `commit_verified_artifact`; the tests that exercise a *real* artifact
  file (`test_storage_artifacts.py`'s orphan/GC/redaction tests, `test_storage_recovery.py`'s
  restart test) were updated to call `commit_verified_artifact` too, so they now exercise the
  actual recommended path instead of the bypass.

4. Decisions or specification discrepancies recorded

- No new ADR. Routine implementation choices, recorded here per the engineering contract
  rather than filed separately:
  - **Hardened idempotency beyond the minimum.** An early draft used `INSERT OR IGNORE` for
    every commit method, which is idempotent for identical retries but *silently* drops a
    genuinely conflicting row (same key, different content) instead of surfacing
    `ConflictError` — a real bug caught by `work_items`' own unique-task-key test (a second,
    different `work_item_id` reusing a `task_key` was silently ignored instead of raising).
    Every commit method now goes through the same explicit "read-compare-insert" pattern
    (`_commit_idempotent`/`_commit_idempotent_composite`), including for tables where a
    mismatch is currently low-probability (e.g. `datasets`, keyed by content hash) — added a
    separate `manifest_hash` column there specifically to still catch a caller passing an
    internally-inconsistent manifest under a reused `content_hash`.
  - **`work_item`/`usage_event`/`observation`/`approval` IDs are not content-derived**, unlike
    `datasets`/`applications`/`plans`/`runs`/`execution_attempts`/`metric_results` (which key
    off the model's own natural identity or a hash of it). Content-hash columns were added to
    those tables specifically to support conflict detection despite the ID itself carrying no
    content guarantee.
  - **`RunManifest` has no `status` field** (by design — the core model is identity/config
    only, per Prompt 01's ADR 0001). `runs.status` is a storage-layer-only column, defaulting
    to `'created'` and updated via `update_run_status`; the actual state machine (what values
    are valid, who's allowed to transition) is explicitly Prompt 06 (engine) scope — this
    phase only makes the column exist and survive restarts.
  - **`WorkItem`, `UsageEvent`, `Approval` added to `core/models.py`.** The specification's
    §5 internal-model table and §15/§16 prose describe all three, but Prompt 01 didn't define
    them (out of that prompt's stated scope). They were added now, minimally (identity/state
    fields only, no scheduling/budget/policy *logic*), because 02-T1 explicitly requires
    repositories for "work items ... usage and approvals" and there was nothing to persist
    without them. No behavior depends on them yet; Prompts 06 (engine) and 16/17 (budgets,
    policy) own their actual logic.
  - **Single-writer strategy is a process convention, not a lock.** One `Database` instance
    (WAL mode, `busy_timeout=5000ms`) is intended as the sole writer per workspace per the
    prompt pack's explicit MVP scope ("Use local SQLite only"); this phase does not add
    cross-process locking or a daemon, matching "cross-run caches and distributed coordination
    are later work."
  - **`read_bytes` now always re-verifies** (path validation + size + digest) rather than
    trusting a ref it might have just handed out itself moments earlier. This trades a small
    amount of read-time hashing overhead for the guarantee that a read result is never wrong
    regardless of how the `ArtifactRef` reached the caller (freshly written, loaded from the
    database, or passed across a process boundary) — correctness over performance is the
    right default for MVP-scale artifacts; revisit only if profiling in a later prompt shows
    this matters at real workload sizes.
  - **`Storage.commit_artifact_unverified` still does not itself call into `ArtifactStore`**
    (no verification against the real file at commit time unless the caller goes through
    `commit_verified_artifact`, §1a/§1b). This keeps `storage/repositories.py` free of a
    filesystem dependency, matching its existing design (every other `commit_*` method is
    pure DB logic); `commit_verified_artifact` in `storage/artifacts.py` is the recommended
    call site for real usage, and Prompt 03's runners (the first real producers of artifacts)
    should call it rather than `storage.commit_artifact_unverified` directly.
  - **Migration append-only discipline starts being enforced from migration 3 onward.**
    Migrations 1 and 2 were edited in place several times during earlier remediation passes
    before any of this work was committed to version control, so no real deployed database
    was ever affected by those edits — but the practice itself was wrong regardless of git
    history, as §1b's review correctly pointed out, and continuing it would make every future
    schema fix indistinguishable from a fresh design rather than a tracked change. From
    migration 3 on, every future schema change is a new migration; migrations 1 and 2 are now
    treated as shipped and are not to be edited again.
