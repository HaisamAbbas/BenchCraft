Phase 07 — Evaluation planning and bounded LLM reasoning
Status: COMPLETE

1. Implemented functionality and changed files

- **07-T1 Evidence summaries** (`src/aibench/inspection/`).
  - `profile.py`: `ApplicationProfile` holds one `ObservationClaim` per capability:
    - `observed`: seen in successful recorded executions of the same app config
    - `declared`: mapped in the config; a contradiction is stated when every recording lacks it
    - `unknown`: neither, with a minimal integration recipe as the gap

    Evidence cites config JSON pointers or execution IDs. The endpoint is kept as its origin only. The scope text says no source code or architecture was discovered.
  - `dataset_summary.py`: `DatasetSummary` holds present/empty/missing counts per evaluation-view path and reference-status counts. It never contains values. `inferred` claims (`retrieval_task`, `tool_use_task`) carry their stated limitation.
- **07-T2 Plan compiler and validator** (`src/aibench/engine/compile.py`, rewritten).
  - `analyze_plan` collects every finding and classifies it as `invalid`, `missing_information` or `missing_permission`, each either blocking or a warning.
  - `compile_plan` is `analyze_plan` plus a refusal on any blocking finding, so validation and the execution gate cannot disagree.
  - The checks cover:
    - eligibility (unknown IDs; unavailable Golden inputs are now rejected before the run)
    - per-case field coverage (none → blocking; partial → warning with counts)
    - `where` selectors over `case.*` paths
    - the execution→evaluation DAG (`work_graph`, `dag_problems`)
    - seeded sampling
    - budgets that cannot cover the plan
    - aggregation vs. value kind
    - policy
  - `core/plans.py` adds `CasePredicate`, and `CaseSelection` gains `where`, `sample_size` and `seed`. Sampling ranks cases by SHA-256, so it is stable across platforms and Python versions. `schemas/1.0.0/ExecutablePlan.json` is regenerated.
  - `security/policy.py` adds `plugin_denials` (checked before any worker starts) and `allowed_planner_origins`.
- **07-T3 Bounded planning loop** (`src/aibench/planning/`).
  - `catalog.py`: a `MetricOption` per installed manifest, with deterministic eligibility, derived concepts and required parameters (including `oneOf`/`anyOf` alternatives). `concepts_in` is a negation-aware keyword matcher.
  - `drafts.py`:
    - `DraftProposal` is the only thing the planner writes: objectives, metric choices, repetitions, gaps and questions. It has no paths, selection, budgets, parameters or rules.
    - `DraftContext` holds what the user and policy fix.
    - `validate_draft` requires verbatim user objectives and per-concept coverage, and blocks parameters or rules the planner invented.
    - Also: `pending_questions` (hashed, deduplicated), `estimate_spend` and `draft_document`.
  - `template.py`: the deterministic planner, used as both baseline and fallback.
  - `planner.py`: `PlannerProvider` (a narrow protocol) and `plan_with_model`.
    - Seven read-only in-memory tools; unknown tools are refused.
    - Bounds: 6 model calls, 12 tool calls, 2 repairs, 60k tokens.
    - Any failure falls back to the template.
    - The model is not contacted when the plan already needs a permission the policy lacks.
  - `openai_provider.py`: an OpenAI-compatible Chat Completions provider.
    - Allowed endpoints: loopback, or an HTTPS origin in `allowed_planner_origins`.
    - The API key is a secret reference, redacted from errors.
    - No redirects; 2 MB response cap; defensive parsing.
  - `service.py`: input gathering and drafts written atomically with revisions and archives.
  - `benchmark.py`: the §23 planner benchmark scorer.
- **07-T4 Commands.**
  - `cli/inspect.py`: `aibench inspect APP [--dataset] [--run ...]`. It refuses runs recorded with a different app config hash.
  - `cli/plan.py`: `aibench plan` writes `plan.json` plus `plan.draft.json` with:
    - the profile and dataset hashes
    - objectives, rationale and gaps
    - pending questions
    - classified findings and coverage
    - a spend estimate
    - provenance

    Exit codes: 0 executable, 2 information or invalid, 4 permission. `--revise` archives the previous revision. `plan validate` moved here from `cli/run.py` and now reports findings, coverage and the estimate. `cli/main.py` registers both commands.
- **Examples:** `examples/planner/openai.provider.json`.
- **Tests:** `tests/planning_support.py` plus eight new test files (81 tests, listed in section 2). Updated: `tests/test_cli_run.py` (whitespace-insensitive assertion).
- **Docs:** ADR 0006 and the ledgers (`tickets.md`, `requirements-matrix.md` with 7 new rows, `phase-status.md`).

4. Decisions or specification discrepancies recorded

- **ADR 0006** records:
  - the evidence model
  - the finding classes and single gate
  - the plan-format additions
  - the derived DAG (user-authored selector graphs are Prompt 11)
  - what the planner may and may not write
  - draft validation rules
  - template rules
  - loop bounds and fallback
  - provider egress rules
  - revisions
  - the benchmark and its limitation
- **Behaviour change from 06:** a metric whose required Golden field no selected case has is now rejected before the run. Before, it scored `not_applicable` for every case.
- **Metric parameters and pass/fail rules come only from the user** (`--params`, `--rule`), following §3: a harness must not invent a schema or threshold. Missing ones become pending questions.
- **Benchmark limitation:** the fixtures were written by the same author as the template and have had no second review. The 1.0 scores show the rules behave as designed; they are not evidence that the approach generalizes. No live-model comparison was run.
- **Independent review:** an adversarial subagent found 4 major and 12 minor issues.
  - Major issues, all fixed:
    - label probing through model-authored selection (selection removed from proposals)
    - dropped or relabelled objectives
    - invented parameters and thresholds
    - malformed provider responses crashing the planner
  - Minor issues, all fixed:
    - revision and archive handling
    - duplicate question IDs
    - the benchmark ignoring unjustified selections
    - keyword negation
    - plugin-load consistency
    - typos misclassified as permission problems
    - a briefing sent before permission checks
    - plaintext planner endpoints
    - tokens without usage
    - failed attempts counted as evidence
    - no draft written for a denied provider
    - version-dependent sampling
- **Commit mixing:** `a5f527c` (the Prompt 06 commit) already contains early Prompt 07 pieces: the selection fields, `case_field`, `resolve_binding`/`applicability_problems`, and a first `analyze_plan`. The rest of Prompt 07 is uncommitted. History was not rewritten.
