Phase 08 — Persistent two-way conversation and typed actions
Status: COMPLETE

1. Implemented functionality and changed files

- **08-T1 Sessions and decisions.**
  - `src/aibench/core/sessions.py` defines the §5 records: `BenchmarkSession`, `ConversationTurn`, `PendingQuestion`, `DecisionRecord`, `ActionRequest`, `SessionChoices` and `PlanPatch`. They are exported as JSON Schema: 7 new files in `schemas/1.0.0/`, and `core/schema_export.py` includes them.
  - Migration 7 (`storage/migrations.py`) adds the tables `sessions`, `conversation_turns`, `decision_records`, `pending_questions` and `action_requests`. It enforces:
    - a unique revision per session, with compare-and-set on `sessions.revision`;
    - one stored turn per delivery ID, and one reply per turn;
    - one record per action ID.
  - `src/aibench/sessions/store.py` (`SessionStore`) implements these. Each decision links its source turn, revision, superseded decision, structured change, choices, content-addressed plan file and hash, and validated draft. Each turn links its decisions and actions. Each action links its turn, expected revision, authorization quote and run ID.
  - `src/aibench/cli/sessions.py` adds `aibench sessions list` and `aibench sessions show ID [--json]`, registered in `cli/main.py`.
- **08-T2 Conversation loop.**
  - `src/aibench/conversation/agent.py` (`ConversationAgent`) runs one bounded model turn per message (6 model calls, 12 tool calls, 60k tokens) over narrow tools:
    - reading: `get_session_state`, `show_plan`, `read_profile`, `summarize_dataset`, `list_evaluators`, `describe_evaluator`, `explain_metric`
    - changing: `propose_plan_patch`, `ask_user` (at most 2 questions, benchmark fields only)
    - results: `get_run_status`, `list_failures`, `get_case_evidence`
    - acting: `request_action`
  - Every reply stores a harness-computed `TurnOutcome` whose `status_line` says whether the turn explained, changed the draft or acted, and that an active run continues.
  - A redelivered message returns the stored outcome, and the model is not called again.
  - Credentials are redacted before a message is stored or sent.
  - `src/aibench/sessions/drafting.py` turns a `PlanPatch` into new choices, then builds a draft with the 07 services (`gather_inputs`, the template planner, `validate_draft`). The draft keeps missing information and missing permission separate.
  - Answers are reused: `planning/template.py` gained a `concepts` mapping, so a "Which concept does … mean?" answer stays part of the choices.
- **08-T3 Real services.** `src/aibench/sessions/controller.py` (`SessionController`) uses the headless commands' services:
  - `compile_plan` (the execution gate, run again at start), `create_run` and `execute_run` (same engine, lease and freezing), and `run_status`;
  - stored metric results and attempts, for failures and case evidence.

  Runs execute as asyncio tasks, and the model call runs in a worker thread, so the conversation stays responsive during a run. Pause, resume and cancel go through `RunController`; for a run not executing in this process, they re-enter `execute_run`. Each is recorded as an action plus a `control_requested` run event. `run_events(after=…)` replays committed events.
- **08-T4 Action boundaries.**
  - A patch or answer made against an old revision is rejected as `stale`.
  - `start_run` targets the reviewed current revision. The compiled plan hash must match the reviewed revision. Missing information gives `blocked`; missing permission gives `denied`.
  - Action IDs are deduplicated. One active run per session, with the run slot claimed by compare-and-set across processes.
  - A scope change during a run makes a new revision and leaves the run's frozen plan untouched. Questions never touch the run.
  - An assistant patch must quote the user and ground every value in the user's words; a refusal in the quoted sentence or any later sentence overrides an earlier request.
  - An assistant action must quote an explicit request (the action verb, about the run, no negation, not a question), or be a whole-message "yes" to an offered plan. A later refusal overrides an earlier request. It can only start a revision the user was shown.
  - Case inputs and outputs reach the assistant only when the new policy flag `share_case_content_with_assistant` is set. Reference answers and free-text reasons never do.
