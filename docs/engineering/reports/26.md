# Prompt 26 — Evaluation opportunities and candidate dataset discovery

Status: COMPLETE for bounded opportunity reporting, repository candidate discovery, and
explicit dataset selection. This does not complete the conversational evaluation loop or
validate semantic quality of repository tests/evaluation suites.

## 1. Implemented functionality and changed files

- **26-T1 — evidence-backed opportunities.** Added `src/aibench/planning/opportunities.py`
  to present the existing planner catalog's deterministic eligibility as objective and
  concept opportunities. It reports required application/dataset evidence, usable case
  counts, unavailable metrics, user inputs and concept-specific gaps. Inferred source imports
  and reference context do not make runtime retrieval available. Added the read-only
  `aibench plan opportunities --app APP --dataset DATA --objective TEXT [--json]` command in
  `src/aibench/cli/plan.py`; `src/aibench/planning/service.py` gathers these inputs without
  inventing an output plan path. The command does not write a plan or invoke the application.
- **26-T2 — bounded repository candidates.** Added
  `src/aibench/inspection/candidates.py` and lazy public exports from
  `src/aibench/inspection/__init__.py`. It validates only policy-approved, bounded JSONL
  candidates: at most 32 files, 8 MiB per file and 32 MiB total. The existing policy's
  `inspection_roots` and any configured `data_roots` are enforced before candidate content is
  read. Results carry path evidence,
  content identity, schema-level compatibility, provenance/confidence, field counts and
  limitations; they never return input, reference or expectation values. Unreviewed
  `synthetic_unverified` cases are incompatible. Tests, evaluator clues and invocations remain
  path-only and are not promoted or executed.
- `src/aibench/cli/inspect.py` adds this typed inventory to `inspect --source` JSON/text
  output. The existing source inspector remains the source of policy-root, secret-file,
  symlink, parser and walk-budget controls.
- **26-T3 — dataset choice.** `src/aibench/cli/chat.py` keeps an explicitly configured or
  `--dataset` path as the selected source. When creating a new session without one, it reuses
  a sole compatible content identity only if the current policy approves repository inspection
  and any configured `data_roots` permits the candidate.
  Identical-content copies collapse to one choice. Distinct candidates cause an interactive
  choice or, in headless chat, a focused question naming the paths and requesting `--dataset`.
- Added `tests/test_opportunity_discovery.py` and `tests/test_dataset_discovery.py`; extended
  `tests/test_cli_chat.py`. Updated support, product alignment, requirements, ticket/test and
  phase ledgers. Saved final JUnit at
  `docs/engineering/evidence/26/focused-junit.xml`.
- No broad refactor, evaluator-vendor dependency, new parser language, evaluator execution,
  dataset promotion, or black-box behavior was added. The existing reference isolation and
  candidate review/promotion workflows were reused.

## 4. Decisions and scope limits

- “Compatible” means valid, non-empty JSONL with the current case schema and no
  `synthetic_unverified` references. It does **not** prove reference correctness, objective
  fit, evaluator suitability, or test-suite quality; the inventory labels this limitation.
- Objective matching uses the existing deterministic vocabulary. It makes gaps visible and
  asks when wording is unknown; richer natural-language planning remains Prompt 27 work.
- Dataset auto-selection requires the existing policy to approve the project in
  `inspection_roots` and stay within configured `data_roots`. It does not widen that policy. Application and runner configuration
  remain explicit; this ticket does not infer an invocation and run project code.
- No new ADR was needed. Prompt 24's v3 conflict decisions remain in
  `docs/engineering/product-alignment-v4.md`; Prompt 26 does not change them.
- The full repository suite and all live/human validation remain unrun for Prompt 26.
